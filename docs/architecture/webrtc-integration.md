# WebRTC peer integration status

## Current code

`NativeWebRtcPeer` is now a managed native session implementation and implements `IPeerConnection`. It creates/deletes peers, applies only verified negotiation messages, keeps separate reliable ordered control/bulk channels, bounds incoming/outgoing queues, applies send backpressure, and reports the selected ICE route after readiness. Signed certificate metadata must have been applied and native DTLS must be connected before identity/encryption status becomes active. A live authorization monitor closes the native peer after pairing revocation; send/read operations also recheck authorization. Callback delegates remain rooted through the native runtime's final cleanup, and the module stays loaded for the process lifetime because P/Invoke caches export addresses.

`DeviceSessionFactory.BeginOutgoingNativeAsync` and `AcceptIncomingNativeAsync` bridge persisted pairing grants to this session and dispose resources on start/apply failures. Integration tests use those exact entry points, transfer control traffic and a 64-KiB bulk chunk over real loopback peers, reject unauthorized bulk use, and verify native closure after revocation. This has not yet been wired to the application's real WebSocket signaling listener or screen/video UI.

`DirectPeer` is the security and route-selection boundary. It tries the direct route, uses the relay route only for route-availability failures, and rejects a peer if its reported device ID, DTLS encryption, or identity verification does not match. Caller cancellation stops both attempts. The tests exercise this behavior with an in-process peer connector.

The product WebRTC connector is not implemented yet. With user authorization, Microsoft Build Tools, MSVC, the Windows SDK and CMake are now installed. `artifacts/native/datachannel.dll` has been built from verified upstream v0.24.6 archives with media support and static Mbed TLS 3.6.7 (DTLS-SRTP enabled). The native smoke check loads the x64 DLL, creates a peer and control channel, and verifies that the generated offer contains a DTLS fingerprint and encrypted SCTP transport. A separate C# interop loopback diagnostic connects two actual native peers, exchanges SDP/ICE through in-process callbacks and verifies the exact binary message received over their data channel. It binds only to 127.0.0.1 and uses no STUN/TURN server. This diagnostic does not authenticate a paired remote device; the main UI still cannot establish a product session.

Run `scripts/build-native-from-archives.ps1` to reproduce the native build. The script verifies pinned archive SHA-256 values, initializes the x64 Microsoft developer environment, builds into `.native`, and writes the DLL hash, source manifest and dependency licenses into `artifacts/native`. Git transport failed on this host, so this build uses the official GitHub codeload archives at the release tag and pinned submodule commits. `scripts/test-native-library.ps1` repeats the native smoke check without installing tools or contacting another device.

Run `scripts/test-native-loopback.ps1` for the two-peer native transport check. Native delegates remain rooted through peer deletion and global cleanup; callback exceptions are contained and propagated into the diagnostic result. This is test-only interop, separate from the authenticated connector required before screen/input/file capabilities can be enabled.

`AuthenticatedSignalingInbox` now verifies that each incoming message targets the local device, comes from a currently paired identity, and has a signature from the public key whose fingerprint matches the claimed source ID. It rechecks authorization after signature verification and records nonces only after acceptance. Keep one inbox alive across reconnects to retain its bounded replay history. `SignalingClient.ReceiveAuthenticatedAsync` exposes this boundary, and the real two-client loopback signaling integration uses it in both directions. Session capability negotiation and binding the verified SDP to native peer creation still need to be connected before enabling product sessions.

`WebRtcNegotiation` now signs the whole SDP/ICE payload together with a fresh session ID and capability grant. The receiver checks the expected peer, session, role, grant and SHA-256 DTLS fingerprint before returning the payload for native use; a certificate fingerprint cannot change within a session. Managed native-integration tests feed accepted messages into actual native peers and verify binary delivery. Separate negative tests reject tampered SDP, mismatched grants, cross-session messages, certificate changes and ICE line injection. These checks run in the test harness; the product connector, enrollment exchange and main-window session lifecycle still need wiring.

The main window initializes a single `DeviceSessionFactory` after loading its protected identity. The factory reads active pairings from `DeviceStore`, shares one authenticated inbox across reconnects, generates fresh outgoing session IDs and validates incoming offers before returning any metadata for native creation. `WebRtcNegotiation` requires a live pairing resolver and rechecks authorization for outbound as well as inbound messages. A separate store instance's persisted revocation is visible to existing negotiation objects and closes the associated managed native peer.

## Pinned native dependency

The desktop consumer now demultiplexes `PRF1` file packets from `PRD1` desktop packets. File metadata/control uses the control channel; content and end markers share the ordered bulk channel to prevent cross-channel end-marker races. `SessionFiles` obtains a local destination before accepting, uses the existing atomic/hash-verifying receiver, bounds metadata/chunks and acknowledges only after finalization. Integration covers duplex transfer, rejection, zero-byte completion and receiver cancellation while synthetic desktop frames remain active.

Offline enrollment now uses signed invitation/request/receipt files with a five-minute single-use token and HMAC binding. The local LAN host registers only its selected active paired peer plus itself and stores certificate/token state under DPAPI. Signed connection configuration binds service identity, recipient, endpoint and certificate pin. The WSS/native integration rejects an incorrect pin and passes under the normal Windows profile. Restricted sandbox Schannel/DPAPI is not a valid substitute for the desktop-profile result. The separate protected LAN-state restart probe is implemented but has not yet run successfully under a normal profile because subsequent automatic approval was unavailable.

The main window retains one `WindowsInputControl` for its entire lifetime, so pending releases from an ended session are drained before a reconnected session can inject new input; an old retry worker cannot release a new session's fresh key-down.

`PeerSessionHost` now owns one real signaling socket and one paired native session. It routes signed SDP/ICE by peer/session, authenticates discarded stale messages through the shared inbox, automatically accepts authorized incoming offers, and shuts down native state on signaling failure. A signed session-close retains signaling availability; late messages arriving after native teardown cannot take down the service connection. The network integration check establishes actual native channels through a loopback ASP.NET WebSocket service, sends control and 64 KB bulk data, disconnects/reconnects with a fresh session ID and verifies service revocation closes the receiver's native session. This is a same-machine network integration check, not a two-physical-PC or Internet performance result.

The WPF window exposes service credentials, paired-device connect/disconnect and live native route/status. Closing the window awaits desktop/host cleanup before disposing the signing identity. `DesktopSession` is the single native message consumer while a screen-control session is active. It sends bounded, ordered JPEG chunks over the control channel and only accepts input during a requested share. `RemoteDesktopWindow` retains only the latest pending render frame and serializes a bounded input queue; focus loss/F12 purge unsent input and enqueue a release marker behind any in-flight input. Failed stop/release delivery closes the native peer. `WindowsInputControl` retains failed/partial releases and retries only the tracked release events when the Default desktop is available. GDI/JPEG is an interim baseline; WGC/H.264, connected file-transfer flows, enrollment exchange and production TURN routing remain pending. Bulk messages are rejected by the desktop consumer until the file demultiplexer is integrated.

Use libdatachannel **v0.24.6** and its documented C API. Build the shared library with Microsoft Visual C++ in Release mode, retaining the upstream license and all dependency notices. The project currently targets the data-channel and media APIs because file/input transport uses ordered data channels while screen video will use WebRTC media tracks.

Before loading the native library, verify its SHA-256 against the build artifact manifest and confirm the expected exported C API symbols. Ship the DLL and all runtime dependencies beside the signed client; do not load an arbitrary copy from the current directory or `PATH`.

## Adapter contract

The future native adapter must:

1. Create a peer connection with the configured STUN/TURN servers and enforce relay-only ICE policy for the relay attempt.
2. Exchange SDP and ICE only through the authenticated signaling client.
3. Bind the peer signing identities, protocol version, negotiated capabilities, ephemeral ECDH keys, and DTLS certificate fingerprint in the signed session transcript before enabling any channel.
4. Expose route `Direct` only when the selected ICE pair is direct and route `Relay` only when a TURN candidate is selected.
5. Create separate ordered channels for control and bulk transfer, with bounded queues and cancellation.
6. Reject plaintext, failed DTLS fingerprint verification, unknown devices, revoked grants, mismatched peer identities, and unsupported capabilities without retrying through a less secure mode.
7. Keep native callback delegates alive until the corresponding libdatachannel objects are deleted; dispose callbacks and peer objects after close has completed.

See the pinned [C API](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/DOC.md), [Windows build instructions](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/BUILDING.md), and [release](https://github.com/paullouisageneau/libdatachannel/releases/tag/v0.24.6).
